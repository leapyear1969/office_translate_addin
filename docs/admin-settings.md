# 网页管理后台权限

入口：`/admin/settings`。登录后，有权限的账号会在顶部看到“管理员设置”。

## 使用

1. 点击“添加管理员”，输入账号登录所属的租户 ID。
2. 选择邮箱或用户对象 ID，填写对应账号。邮箱仍通过服务端 Graph `/me` 核验，不根据前端传入邮箱授权。
3. 选择“指定租户”并填写租户 ID，或选择“所有租户（含以后新增）”。
4. 选择角色：查询管理员只能看报表；权限管理员可以查看、修改所有后台管理员，并可授予全租户查询权限。
5. 点击“保存更改”。修改、移除操作在保存前都是草稿；可用“放弃更改并重新加载”恢复。

保存成功后，新请求立即使用新权限，不需要重启。移除账号后，即使该账号仍持有有效登录令牌，也不能再查询后台。已经返回给浏览器的数据不会被远程清除。不能移除当前账号自己的权限管理资格或修改自己的登录身份；需要由另一位权限管理员处理。至少保留一位权限管理员。并发修改返回冲突提示，不覆盖他人的保存。

## 首次升级和初始化

部署代码、运行 `npm run build` 并重启单实例后端。无需新增 Entra 回调地址，继续使用 `/admin/usage`；登录完成后进入“管理员设置”。

首次访问后台 API 时，将非空 `ANALYTICS_ADMINS` 一次性导入 PostgreSQL 的 `usage_analytics.admin_settings` 表。已有 `tenants:["*"]` 的管理员默认成为权限管理员；其他管理员默认只能查询。可用显式布尔值 `can_manage_admins` 覆盖导入时的角色。

如果原配置为 `[]`，系统不会开放匿名注册管理员。维护人员需先配置一个可信的初始账号，例如：

```dotenv
ANALYTICS_ADMINS=[{"tenant_id":"<登录租户 GUID>","email":"admin@example.com","tenants":["*"],"can_manage_admins":true}]
```

初始化成功后，后续管理员配置以数据库为准，`.env` 可恢复为 `ANALYTICS_ADMINS=[]`；无需继续手改 JSON。环境变量不会在重启时覆盖网页配置，也不会恢复已删除账号。若导入的旧名单没有任何权限管理员，需要维护人员在数据库中修正指定账号的 `can_manage_admins` 后重新进入页面；不要删除整张设置表来恢复权限。

新表独立于统计报表数据，不包含在报表的 coverage 元数据里，不改变统计保留期限。数据库不可用时，管理员接口返回 503，不退回环境变量绕过已经撤销的权限。使用现有数据库连接与串行队列；单实例要求不变。新表需要纳入数据库备份；旧版本不读取此表，回退旧代码前需核对其环境变量权限，避免恢复旧授权。

本次实现和测试不直接更新线上服务或生产数据库。部署后需使用真实管理员账号验收登录、添加、修改和撤销权限。
