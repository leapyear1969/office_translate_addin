# 网页管理后台权限

入口：`/admin/settings`。登录后，有权限的账号会在顶部看到“管理员设置”。

## 使用

1. 点击“添加管理员”，输入账号登录所属的租户 ID。
2. 填写该登录租户内的用户对象 ID（Entra 用户页面的 Object ID）。邮箱/UPN 可被转移，不再用于授权；来宾账号应填写登录租户中的来宾对象 ID。
3. 选择“指定租户”并填写租户 ID，或选择“所有租户（含以后新增）”。
4. 选择角色：查询管理员只能看报表；权限管理员可以查看、修改所有后台管理员，并可授予全租户查询权限。
5. 点击“保存更改”。修改、移除操作在保存前都是草稿；可用“放弃更改并重新加载”恢复。

保存成功后，新请求立即使用新权限，不需要重启。移除账号后，即使该账号仍持有有效登录令牌，也不能再查询后台。已经返回给浏览器的数据不会被远程清除。不能移除当前账号自己的权限管理资格或修改自己的登录身份；需要由另一位权限管理员处理。至少保留一位权限管理员。并发修改返回冲突提示，不覆盖他人的保存。

## 首次升级和初始化

部署代码、运行 `npm run build` 并重启单实例后端。无需新增 Entra 回调地址，继续使用 `/admin/usage`；登录完成后进入“管理员设置”。

首次访问后台 API 时，将非空 `ANALYTICS_ADMINS` 一次性导入 PostgreSQL 的 `usage_analytics.admin_settings` 表。已有 `tenants:["*"]` 的管理员默认成为权限管理员；其他管理员默认只能查询。可用显式布尔值 `can_manage_admins` 覆盖导入时的角色。

如果原配置为 `[]`，系统不会开放匿名注册管理员。维护人员需先配置一个可信的初始账号，例如：

```dotenv
ANALYTICS_ADMINS=[{"tenant_id":"<登录租户 GUID>","user_oid":"<已核对的用户对象 GUID>","tenants":["*"],"can_manage_admins":true}]
```

初始化成功后，后续管理员配置以数据库为准，`.env` 可恢复为 `ANALYTICS_ADMINS=[]`；无需继续手改 JSON。环境变量不会在重启时覆盖网页配置，也不会恢复已删除账号。若导入的旧名单没有任何权限管理员，需要维护人员在数据库中修正指定账号的 `can_manage_admins` 后重新进入页面；不要删除整张设置表来恢复权限。

新表独立于统计报表数据，不包含在报表的 coverage 元数据里，不改变统计保留期限。数据库不可用时，管理员接口返回 503，不退回环境变量绕过已经撤销的权限。使用现有数据库连接与串行队列；单实例要求不变。新表需要纳入数据库备份；旧版本不读取此表，回退旧代码前需核对其环境变量权限，避免恢复旧授权。

本次实现和测试不直接更新线上服务或生产数据库。部署后需使用真实管理员账号验收登录、添加、修改和撤销权限。

## 从邮箱授权版本升级

升级后，数据库及环境变量中的旧邮箱条目均不再提供查询或权限管理权，且不会通过 Graph 自动绑定当前邮箱持有人。升级前必须核对原获批人员的身份，以及其在登录租户内的对象 ID。

1. 备份数据库并读取当前数据库名单，确认至少有一位 `user_oid` 类型、`can_manage_admins:true` 的可信管理员。不要只检查 `.env`，初始化后的名单以数据库为准。
2. 如果全部权限管理员都是邮箱类型，在升级前通过现有管理页面添加一位已核对对象 ID 的权限管理员，并使用该账号验证登录。旧页面的自身保护不允许直接替换当前账号的邮箱身份，需先添加对象 ID 条目。
3. 升级后用对象 ID 管理员登录，核对并迁移剩余邮箱条目，或删除不再需要的条目。页面显示旧邮箱供人工核对，但不会把它自动转换成对象 ID。保存要求所有条目都有对象 ID。
4. 同步清理环境中的旧邮箱配置，避免旧代码回退时恢复邮箱授权。不要删除设置表或用环境名单覆盖数据库；若已升级且全部管理员被停用，需由数据库维护人员在停服、备份及核验身份后恢复一个对象 ID 管理员。

## 配额与代理

后台未携带有效 Bearer 格式的请求先按 IP 限制为每分钟 120 次；Bearer 验证失败的请求计入同一未认证配额。有效令牌验证后，后台按已验证的 `tid + oid` 使用独立的每分钟 120 次配额，同一账号更换令牌不会重置配额。匿名配额耗尽不会阻断共享出口的有效账号，不同账号和不同租户的配额互不影响。

应用保持 `trust proxy=false`，不采信客户端自行传入的 X-Forwarded-For。部署时需在可信入口设置连接和请求防滥用限制：带 Bearer 的请求仍需先验证签名才能决定其身份配额，应用的失败计数不能代替入口层的验签资源保护。如需启用代理信任，应根据实际代理地址和链单独配置，不能直接设为 true。配额使用进程内存，重启重置；继续使用单实例部署。

## 后台浏览器策略与依赖补丁

后台 `/admin/*` 与 `/admin.html` 使用 CSP、`X-Frame-Options: DENY` 和 `X-Content-Type-Options: nosniff`。后台只能作为顶层页面打开；Office 的 Word、Outlook taskpane 和其他插件页面不添加禁止嵌入策略。脚本和样式仅从同源加载，禁止内联脚本、eval、对象、表单提交及子框架；API/MSAL 连接允许同源、配置的 AUTHORITY、Microsoft 实例发现端点和适用的中国云登录别名。

登录仍跳转 Entra 并回到已有 `/admin/usage`，无需新增回调地址。访问令牌过期时可使用刷新令牌续期；刷新令牌过期或需重新授权时，页面提示重新登录，由用户点击登录按钮继续，不尝试隐藏 iframe。若改用其他身份云或自定义 authority，应同步核验其发现与令牌端点是否受 CSP 允许。

生产安装须同时更新 `package.json` 和 `package-lock.json`，用 `npm ci`、`npm run build` 构建，再按现有方式重启后端。覆盖 `qs=6.16.0` 修复两项解析/序列化公告；仅在 MSAL Node 下覆盖 `uuid=11.1.1`，保留 CommonJS 的 v4 API，避免本次升级 Express/MSAL 主版本。覆盖超出了上游依赖范围，后续升级需复测，待上游原生依赖已修复版本后删除 overrides。核验命令：`npm audit --omit=dev --registry=https://registry.npmjs.org`。开发工具链公告仍需另行处理，不能把生产审计为零理解为全依赖审计为零。

部署后检查 GET/HEAD `/admin/usage`、`/admin/api`、`/admin/settings`、`/admin.html` 的响应头。若代理直接提供静态文件，必须配置等效后台策略或让这些请求经过 Node，否则会绕开中间件。用真实管理员验证登录、回调、查询、权限保存、令牌续期与退出；检查浏览器无 CSP 拦截所需资源，后台 iframe 嵌入被拒绝，Office 插件仍可加载。本地自动测试不替代真实 Entra/Office 环境验收。

## 权限变更审计

网页保存权限时，同一事务会追加 `usage_analytics.admin_settings_audit`：已验证操作者的租户/对象 ID、数据库时间、前后版本及发生变化的授权条目。新增、撤销及角色/范围修改均可追溯；无权限、校验失败和版本冲突不会产生成功变更记录。审计插入失败时，权限和版本一并回滚。初始环境导入不是网页修改，不包含伪造的用户操作者；应通过部署记录保留初始化名单来源。

只持久化必要授权字段，不存储令牌、客户端密钥或请求正文。审计表不随统计保留期清理，应纳入备份。应用未提供修改或删除审计的 API；数据库触发器拒绝 UPDATE、DELETE、TRUNCATE，并撤销 PUBLIC 权限。数据库所有者仍能修改触发器或 DDL，生产环境应限制数据库所有者账号及迁移权限，并另行保留数据库审计/备份。

维护人员可只读查询：

```sql
SELECT changed_at, actor_tenant_id, actor_user_oid, previous_revision, revision, changes
FROM usage_analytics.admin_settings_audit ORDER BY revision DESC;
```
