# 用户使用与 API 用量后台：V2 简化实施方案

日期：2026-09-11  
状态：已进入实施；2026-09-11 按确认改用 PostgreSQL、复用现有 Entra 应用。  
版本说明：本文件是收敛后的首期实施范围；V1 原文保留供参考，其额外功能不自动纳入本期。

## 1. 目标与取舍

第一版只回答四个问题：

1. 哪些用户在使用，最近什么时候使用，使用频率如何？
2. 翻译与语言检测 API 调用了多少次？
3. 用户使用的是 Word 还是 Outlook？
4. 使用的是 online 网页客户端还是 local 桌面客户端？

采用服务端请求统计，不建设前端行为事件系统，不追踪一次预览从开始到结束的完整过程。后台的“使用次数”统一命名为“翻译请求次数”，避免与用户点击次数、成功交付次数混淆。

## 2. 统计维度

| 维度 | 取值与说明 |
|---|---|
| 用户 | 已验证的 `tenant_id + user_oid`；展示姓名、邮箱，邮箱允许为空 |
| 使用平台 `host` | `word`、`outlook`、`unknown` |
| 客户端类型 `client_type` | `online`、`local`、`unknown` |
| 日期 | 统一按北京时间统计自然日；服务端时间作为依据 |
| API 层级 | 插件后端业务 API、真实上游翻译服务 API |
| API 接口 | 后端区分 detect / translate / translate-word；上游区分 detect / translate |

使用平台与客户端类型独立记录，例如 Word + online、Word + local、Outlook + online、Outlook + local。local 表示桌面 Office 客户端，不表示离线翻译，也不表示模型在本机运行。

客户端通过已有 Office 环境提供平台信息：`OfficeOnline` 映射为 online，`PC` / `Mac` 映射为 local；无法识别或不在本期映射范围内的值记 unknown，不猜测。旧客户端没有附带字段时仍可翻译，统计归 unknown。

平台字段用于分析，由前端提供并经后端枚举校验；用户归属和访问权限只依据后端验证的身份，不依据前端声明。

## 3. 两个后台页面

### 3.1 用户使用

- 概览卡片：所选期间使用人数、翻译请求次数。
- 每日趋势：每日使用人数、每日翻译请求次数。
- 平台分布：按 Word / Outlook 和 online / local 交叉展示人数及翻译请求次数，unknown 单列。
- 用户列表：姓名、邮箱、租户、首次观测翻译请求时间、最近观测翻译请求时间、期间使用天数、期间翻译请求次数、使用过的平台和客户端类型。
- 支持日期、租户、用户、平台、客户端类型筛选；用户支持姓名／邮箱搜索和分页。

用户在多个平台使用时，可以出现在多个分组中；总人数按账号去重，不将分组人数相加。用户列表的平台信息按所选期间展示，不把一个账号永久归入单一平台。

### 3.2 API 用量

- 分开展示后端业务请求总数与上游实际请求总数，不能将两者相加。
- 按接口展示请求数、成功数、失败数。
- 展示每日请求趋势，以及按用户、平台、客户端类型的请求分布。
- 展示上游“提交文本量”，检测和翻译分别统计；不计算费用。
- 使用与用户页相同的公共筛选。

管理后台作为普通浏览器网站访问，不要求先打开 Office。无需用户行为详情页、逐请求日志页或独立故障页面。

## 4. 核心统计口径

| 指标 | 本期定义 |
|---|---|
| 翻译请求次数 | 通过身份与参数校验、进入 `/api/translate` 或 `/api/translate/word` 处理的请求数，包含之后执行失败的请求 |
| 期间使用人数 | 所选日期及筛选范围内至少有一次上述翻译请求的去重账号数 |
| 使用天数 | 所选范围内该账号有翻译请求的自然日数；同一天跨平台使用仍只计一天 |
| 首次／最近使用 | 已观测翻译请求的最早／最晚服务端开始时间；产品级维护，不随页面筛选重新定义；只登录或检测不更新 |
| 后端业务 API 请求数 | 通过身份与参数校验、进入处理的 detect、translate、translate-word 请求数；不包含认证失败、参数拒绝或限流拦截 |
| 上游 API 请求数 | 服务端实际执行的每次上游检测或翻译请求尝试；发出后超时、失败也计数；发出前配置检查失败不计 |
| 后端请求成功／失败 | 业务处理正常生成结果为成功，执行异常为失败；不表示 Office 已成功显示或写回 |
| 上游请求成功／失败 | HTTP 成功且接口响应结构有效为成功，HTTP 错误、超时、网络异常或无效响应为失败；后续 Word 结构校验问题不改写上游请求结果 |
| 上游提交文本量 | 实际提交的 `Text` 字段按 JavaScript `length` 累加，即 UTF-16 代码单元数；包含提交文本内的标记、空白和重复提交，不含 JSON 外层字段 |

补充规则：

- `/api/detect` 包含自动预检，参与 API 用量，但单独检测不使账号成为使用用户。
- `/api/me`、登录、管理查询、健康检查不进入业务 API 用量。
- 一次后端翻译请求可能分成多次上游请求；正常分批、修复重译均按真实调用计数，本期不再单列修复或重试分类。
- Word 自动预览每次实际发送的新翻译请求都计数，不合并成一个长会话。页面标明“包含自动预览刷新”。
- 用户主动重试或网络层实际重发属于新的 API 请求，不按相同内容去重。内部统计写入不得重复累计同一次请求。
- 提交文本量是工程用量指标，不是可见字数或服务商计费字符数；本期不读取计量规则计算金额，也不与账单对账。
- 每次请求按其服务端开始日期归属；跨午夜完成仍更新开始日。上游请求按自身开始日期归属，不强制跟随后端请求日期。
- 首次使用表示采集开始后可观测的首次翻译请求，不代表用户首次安装或真实历史首用。
- 不记录仅打开面板、未发送请求的使用行为；不统计翻译是否最终被阅读、复制、插入或写回。

## 5. 采集与代码接入

| 位置 | 修改范围 |
|---|---|
| `src/shared/api.ts` 及 Word / Outlook 调用入口 | 仅给业务请求附带 `host`、`client_type`；不增加事件队列或遥测请求 |
| `server/app.js` | 在身份和参数校验后记录业务请求；绑定真实账号，向翻译服务传递统计上下文 |
| `server/translator.js` | 在真实上游请求边界记录次数、结果及提交文本量；分批和修复路径使用同一统计封装 |
| 新增服务端统计模块 | PostgreSQL 存储、按日汇总、用户资料维护、清理、管理查询 |
| 新增管理站页面 | 独立浏览器登录、用户使用页、API 用量页 |

上游调用继承当前业务请求的账号、平台和客户端类型。每个请求使用独立上下文或显式传参，不能将当前用户放进共享全局变量，避免并发请求串账。

用户姓名、邮箱复用已有已验证资料，在已有资料获取成功时更新；不为每次统计额外调用 Graph。暂时没有资料时仍按账号键统计，姓名／邮箱显示未获取。

一次请求在结束处统一提交一次聚合结果，失败路径也执行；以开始时间归属日期。请求仍在处理时可暂不出现在报表，进程中途崩溃可能丢失该请求统计，本期接受此限制，不引入待完成请求状态表。

## 6. 最小存储方案

已确认后端为单实例，统计使用独立 PostgreSQL 数据库，通过 `ANALYTICS_DATABASE_URL` 连接。在 `usage_analytics` schema 中使用事务与版本化迁移；数据库连接由有界异步队列串行使用，不阻塞翻译请求等待统计落库。

只建设两张业务表：

| 表 | 内容 | 保留规则 |
|---|---|---|
| `users` | 真实账号键、姓名、邮箱、产品级首次／最近翻译请求时间 | 保留当前账号资料；受控删除时移除 |
| `api_usage_daily` | 日期、账号、平台、客户端类型、API 层级、接口，以及请求总数、成功数、失败数、提交文本量 | 12 个月 |

`api_usage_daily` 以上述维度组合作为唯一键，使用事务增量更新。提交文本量只用于上游行，业务 API 行不重复计量。使用人数、使用天数和平台分布从业务翻译接口的日汇总查询，无需再建操作表或用户行为表。

用户首次／最近时间与对应业务翻译日汇总在同一事务中维护，乱序完成的请求使用最小／最大开始时间更新。普通日汇总清理不重置仍保留的用户首次时间。超出保留期或采集开始前的日期显示不可用，不显示为零。

每日清理过期日汇总；不存正文、译文、邮件主题、文件名、完整 OOXML、令牌、密钥或原始异常消息，也不保存逐请求明细。

应用不新增统计导出、恢复副本或备份任务。PostgreSQL 服务端的自动备份范围须由部署维护人员核实，不能仅因应用没有备份任务就宣称数据库没有备份。允许历史统计因不可恢复故障丢失，重建后明确新的采集起点。

如需删除用户统计，由获授权维护人员通过受控命令按真实账号清理两张表，并先隔离或排空该账号的在途统计写入再完成删除；不提供网页删除入口。本期没有客户端迟到事件队列，不建设 V1 的事件回执和删除边界表。

## 7. 基本权限与可靠性

- 管理站使用普通浏览器 Entra 登录，复用 `.env` 中现有应用，添加 SPA 回调地址，取得面向本 API 的令牌；不能直接复用依赖 OfficeRuntime 的插件登录。
- 服务端配置管理员及可查询租户，支持 `tenant_id + user_oid`，或按此次确认使用 `tenant_id + email`。邮箱必须来自后端核验的 Graph 账号资料，且用户 ID 与令牌一致；不信任前端邮箱。所有管理查询逐次校验身份、权限和租户范围，邮箱资料最多缓存 5 分钟。
- 只提供只读查询，不提供管理网页维护功能。保持受信来源限制，不为新增管理站放开任意 Origin。
- 业务 API 与管理查询分开限流，避免管理员刷新报表消耗翻译请求配额。
- 查询采用服务端分页，默认 50 条、最多 200 条，日期范围不超过已保留的 12 个月。
- 统计失败不得让翻译失败；统计任务采用有界处理，避免数据库锁等待、清理和管理查询长期占用翻译处理链路。
- 统计写入失败输出无内容、无令牌的健康日志；后台展示已知采集起点和缺口提示，不承诺完整审计数据。
- 不建立账号级统计开关；插件中简要说明采集字段、用途及保存期限。

## 8. 实施顺序

1. 配置单实例后端的 PostgreSQL 连接、真实管理员账号及浏览器登录配置，建立两张表和日汇总查询。
2. 接入后端业务与上游请求统计，验证分批调用计数。
3. 前端附带 Word / Outlook、online / local 字段，保留旧客户端 unknown 兼容。
4. 完成两个只读管理页面、登录权限和公共筛选。
5. 完成自动验证、真实 Office 平台识别验收，再小范围上线观察。

## 9. 验收标准

- 同一用户同一天使用 Word online 和 Outlook local：总使用人数为 1、使用天数为 1，两个平台分组各可看到该用户。
- 一次后端翻译实际发出三次上游翻译：后端翻译请求数为 1，上游请求数为 3，提交文本量按三次实际提交累加。
- Word 同一次预览期间实际发送五次翻译请求：后台显示五次翻译请求，不显示为五次按钮点击或五次成功交付。
- 仅自动检测语言：检测用量增加，翻译请求次数和使用人数不增加。
- 已验证且参数合法的翻译请求执行失败：使用人数及翻译请求数增加，后端失败数增加；实际发出的上游请求照常统计。
- 后端鉴权、参数校验或限流拦截的请求不进入本期用量，也不增加上游次数。
- 上游成功但后续 Word 校验失败：上游成功数保留，后端请求按实际结果统计，不推断 Office 交付结果。
- 缺少或无法识别平台字段时归 unknown，翻译仍正常；在真实 Word / Outlook 网页和桌面客户端验证映射。
- 同邮箱不同租户不合并；并发用户的上游用量不串账；未授权管理员无法查询其他租户。
- 统计库不可写或管理查询繁忙时，翻译仍可完成；统计缺失不能展示为确认的零用量。
- 日汇总增量更新、跨日归属、人数去重、清理和字段白名单有自动测试；运行现有测试、类型检查及构建。
